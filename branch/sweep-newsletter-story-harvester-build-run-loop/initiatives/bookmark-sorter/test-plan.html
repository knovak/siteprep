Test plan

How we know it works. plan.md ends every phase at a section of this document, so "phase complete" is something that passes rather than something somebody decides.

Numbered references to O1–O8 are the objectives; §n is a section of spec.md unless it says plan.md.

1. What testing is for here

objectives.md measures this initiative by how much of the pile gets resolved, not by how well it is organised. That gives the test plan an unusual top-level rule: a test earns its place by protecting a verdict, or by protecting the speed at which verdicts are made. A test that pins a detail no objective depends on is decoration, and this document deliberately has fewer of those than a coverage target would produce.

It also means two things that are not usually tests are treated as tests here: a measured triage rate (§12's instrument, first taken in phase 2) and a real pile going in and coming back out intact (O1 and O7). Both are in §4 with pass conditions, alongside the ordinary kind.

3. Fixtures

Committed under this initiative, small enough to read and diff:

  • export-small.html — a Netscape bookmark export covering the cases that

break parsers: nested folders, a folder with no items, an item with no ADD_DATE, a <DD> description, unicode in titles and paths, an entry with a javascript: URL, and two entries whose URLs differ only by utm_*.

  • export-overlap.html — a second export sharing roughly half its items with

the first, for the merge rules.

  • export-large.html — generated, 10,000 items, for the grid and the

ingestion path. Generated by a committed script rather than committed itself.

  • proposals.json — a §8.2 proposals file, including one URL that is not in

the collection and one proposed tag that already exists on some of its items.

  • export-v1.json — a hand-written bookmark-sorter/v1 document, so import

is tested against a file the code did not write.

4. Phase exit tests

Each section is the gate for the matching phase in plan.md §3.

Every row beginning Measured: needs a person and a real pile, as does §2's once-per-phase sitting. plan.md §7 names that as the plan's largest scheduling dependency, and the consequence here is worth stating plainly: a phase can be entirely written, fully green, and still not exit. "Code complete" and "phase complete" are two states, and only the second is what §3 gates on.

4.0 — Host spike

Not software, so the exit is evidence rather than a passing suite: every row of §10's table filled in with what was actually observed, and a decisions.md entry naming the surface.

Three rows have pass conditions sharp enough to write down, because they are the ones that decide the project rather than a feature. The first of them changed on 2026-08-17 and the old one is worth stating, since this section was written around it: it used to be "a collection's worth of rows can be got out of the host", failing O7 outright. Deciding that the app streams its own export (decisions.md) means no host can fail that, so what is observed here is a ceiling rather than a capability.

  • Outbound HTTP to arbitrary URLs — a normal page, a 404 and an unreachable

host all behave as the code asks, within a timeout the code sets. This now leads, being the only row left that can change the design: failing it moves pass 1 behind the same paid vendor as pass 2 (plan.md phase 0). A bounded batch of ten concurrent fetches also completes in one request; record its elapsed time so phase 3 starts with evidence rather than an assumed batch size.

  • A response large enough to carry the pile out — ten thousand items come out

through the app's own streamed bookmark-sorter/v1 document, by an ordinary user and parse with the expected item count. A platform or database dump does not satisfy this row even where one exists. Failure here is a size: record the received byte count, because that number is what sizes the chunking export and import then need on both sides. Re-import cannot be an exit condition before phase 1 builds ingestion; its no-op semantics remain covered by §4.1 and §4.5.

  • A server-side secret store with a server-side place to call from — a value

can be held that the browser cannot read, and an outbound call can be made from a place that can read it. Failing this switches pass 2 off and nothing else.

4.5 — The round trip

The test O7 actually makes, in three parts:

  1. Export → import into the same collection is a no-op. Same items, same

tags, same verdicts, same notes, no duplicates, nothing changed.

  1. Export of a selection is self-describing. The file records the expression,

carries exactly the selected items, and carries no captures.

  1. **Export → import into a different collection** (§9.1) brings items, tags

and verdicts across; the source is unchanged; the destination's items show their pictures immediately from the URL-keyed cache without a new capture.

Plus: importing export-v1.json, a file the code did not write, works; and an import never overwrites an existing verdict or note — a rule stated in §4, §5.1 and §9, and therefore worth one test per surface rather than one in total.

The proposals file (plan.md §5.7) is the other half of this phase, and proposals.json is the fixture built for it — including the two cases that decide whether it is safe:

6. What is not tested, and why

  • The vendor's rendering quality. Not ours, not stable, and §3 already

accounts for the failure mode by preferring a visible hole to a confident wrong picture.

  • Real websites. The capture tests run against a fixture server; a suite that

fetches the live web fails for reasons that have nothing to do with the change under test.

  • The rate target. There is no threshold to fail against until phase 2

produces a baseline. Until then the rate is recorded, not asserted.

  • Anything held out of the first version — tab harvesting, pushing subsets

into a browser, general sharing. The one thing tested on their behalf is the export format, which is what §11 says makes them cheap later.
