Lessons from similar attempts

Tides App — zph/tides

This small web app geocodes a place, ranks NOAA tide stations by distance, lets the user choose among them, and remembers the selection; it accepts searches “worldwide” while sourcing predictions from NOAA. That combination exposes a coverage distinction: accepting an arbitrary location and finding the closest available station does not establish that the station represents the nearest seafront or an appropriate local tide. (project documentation, NOAA station metadata)

NOAA itself distinguishes harmonic reference stations from subordinate stations. Subordinate-station predictions are adjusted from a designated reference station and provide only high/low predictions, so station type affects both how a prediction is produced and which output is available. (NOAA Tide Predictions help)

OpenSeaMap tide prediction — repository listing

OpenSeaMap lists a public tide-prediction component for its online chart as “not yet visible”; the repository listing shows its last update in September 2019. This is one example where the tide engine existed but the user-facing chart integration remained unfinished. (OpenSeaMap repositories)

Neaps — openwatersio/neaps

Neaps packages a TypeScript prediction engine, station finder, command-line tool, and HTTP API, but explicitly marks its results as not for navigation. Its warning says accuracy depends on the available harmonic data and that the model does not include effects such as storm surge, wind waves, uplift, tsunamis, or climate change. (Neaps documentation)

Snowraven Weather & Tide — product record

Snowraven completed a device-location “Current” flow and a place-or-map-pin “Predict” flow in June 2026 by reusing separate NOAA CO-OPS, Nominatim, and device-location integrations. Its product record also treats provider horizons independently: tide predictions continue beyond the weather window, while unavailable weather is stated explicitly. (Snowraven product context)

SunCalc — mourner/suncalc

SunCalc's moon-time interface records an edge case that a five-day table must be able to express: within one day, the moon can rise and set zero, one, or two times. Its calculation scans a UTC day unless the caller supplies local midnight, so the definition of the location's civil day affects which events appear under a date. (SunCalc documentation)

Browser location and public geocoding

The browser Geolocation API is available only in a secure context, requires express user permission, and can be restricted by Permissions Policy. These constraints make automatic location a permission-dependent path rather than a guaranteed input. (W3C Geolocation specification)

The public OpenStreetMap Nominatim server allows light external use but caps heavy use at one request per second, requires identifying headers and attribution, and asks applications to be able to switch providers. Its public service is therefore a constrained shared dependency rather than an unrestricted production geocoder. (Nominatim usage policy)

Questions this raises

  • Is the first useful version intended to cover NOAA-supported U.S. regions, or arbitrary coastlines worldwide?
  • What makes a seafront or tide station the relevant one when straight-line proximity conflicts with coastline, estuary, island, or waterway geography?
  • Which location's time zone defines the five calendar days: the entered place, the selected seafront, the tide station, or the user's device?
  • How should a day display zero, one, or two moonrise or moonset events?
  • Is the tide display informational only, or is any navigation, safety, fishing, surfing, or flood-planning use expected?
  • What privacy and service-dependency boundaries apply to geolocation, geocoding, and any global tide-data provider?
