2026-11-11 — Add a beta version beside the released simulator

The user asks to "introduce another released version of SBDC as a beta version", whose "code would exist side-by-side with the prod version, in the main branch", deployed "with every merge". The stated purpose: "I could guarantee that source and code would be stable in the current URLs, and the beta version could progress and be substantially modified without destabilizing the current version. Some day, months from now, I could copy the beta code into the released version, and continue to make further modifications to the beta version."

The user also asks that the beta be "easy to access, from both the demos page and the SBDC initiative page", that it "be identical to the current version", and adds: "It would be nice if the simulator itself had a subtle annotation of whether it's beta or released, and when it was last changed."

Decided: the beta's code is beta/, a copy of the code in lib/. The site build builds it and publishes it at demos/SBDC Night Sky/beta/ on every build. lib/, work/ and demos/SBDC Night Sky/ are unchanged. The build adds the "Released" or "Beta" label and the last-changed date to each copy's credit line at publish time.

Alternatives considered

OptionConsequence
Build the beta from beta/ during the site build, and commit no built pageThe published beta always matches its source, and a beta pull request shows only source changes. The site build runs the beta's tests and builder (about two seconds). Chosen.
Commit a built beta page, as work/ does for the releaseA third 245 KB copy of the page in the repository, and it can fall behind its source unless a check rebuilds it anyway.
Commit the beta under demos/SBDC Night Sky/beta/demos/ holds releases, and deploy-demo replaces the demo folder as a whole, so the next release would delete the beta.
Treat work/ as the beta, since the build already publishes it as the test previewThe released source would no longer be at its current paths once the beta changed, which is the stability the user asks for.
Write "beta" and a date into the simulator's codeThe label would have to be changed by hand at promotion, and a released page could ship reading "Beta". The date would be typed rather than derived.

What this settles, and what it does not

  • The 2026-09-11 instruction "remain in dormant state, no additional releases" still governs the released copy. Publishing the beta does not release anything to demos/SBDC Night Sky/, and release-after-testing stays blocked.
  • The released page as served now ends its credit line with "Released · changed 2026-07-20". The file in demos/SBDC Night Sky/ is byte-identical to before; the build adds the label when it publishes. This is the one visible change to the released URL, made because the user asked for the annotation on both copies.
  • The beta is identical to the released simulator on 2026-11-11 apart from its label. No beta change is planned or authorized by this decision; the initiative stays dormant until the user asks for one.
  • Promotion (copying the beta's code into lib/ and work/, then releasing) needs a new explicit instruction. beta/README.md has the steps. It will be the first change to lib/ since adoption, so the adoption manifest's hashes for those code files stop matching from then on.
  • The nine supplied documents are not copied into beta/. Whether the beta gets its own tutorial or specification is open until the beta differs enough to need one.
