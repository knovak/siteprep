# Write an initiative's brief

`brief.md` answers "where does this stand?" for someone who has not read the
initiative. It is a **summary of the initiative's own documents**, not a new
claim about them: the counts are in `work/`, the reviewer duties in
`test-plan.md`, the deferred items in `spec.md`. Everything you write must be
traceable to something already in the repository.

## Before writing

```bash
node scripts/initiatives.mjs brief <slug>          # is one needed?
node scripts/initiatives.mjs brief --json          # every initiative that wants one
```

`absent` or `stale` means write one. `current` means the initiative has not
changed since the last brief - stop, and say so.

Then read, in this order: `initiative.json` for stage and todo list, `wish.md`
for what it is for, `plan.md` for the phases and what is left, `spec.md` for
scope and what was deliberately excluded, `test-plan.md` for what acceptance
requires, `log.md` for what has actually happened, and the `work/` directory
for what exists. Count things rather than estimating them - if you write "13
movement studies", a reader must be able to find thirteen.

## The file

Four `##` sections, all optional; write only the ones with something in them.
Keep each to two or three sentences, or a short list. This is a summary someone
reads in fifteen seconds, and length is what stops it being read at all.

```markdown
# Brief

<!-- Generated by the `write-brief` skill. Do not edit by hand: the next
     refresh overwrites this file. Correct the document it summarises
     instead - spec.md, plan.md, decisions.md - and the fix arrives here. -->

## Done
What exists and works now, concretely. Counts, not adjectives.

## Waiting on others
What people other than the user owe - reviewers, a third party, an upstream
project. Omit the section when nobody is owed anything.

## Remaining work
What an agent will do next, from `plan.md`. Not a restatement of the todo list.

## Optional later
Deferred or optional work, from `spec.md` and `plan.md`. Naming these stops
them reading as hidden obligations.
```

## What never goes in a brief

- **What the initiative needs from the user.** That row is computed from the
  blocked todo items and rendered above your sections. A summary that
  paraphrased a blocker could soften or misstate what the user owes, which is
  the one thing on the page that has to be exact. Do not restate it.
- **The deployment state.** Also computed, in the Deployments card.
- **Anything you cannot point at.** No estimated counts, no inferred progress,
  no "should be ready soon". If the record does not say it, leave it out.
- **A recommendation, a plan change, or a decision.** A brief describes; it
  does not settle anything. A question worth asking goes to `decisions.md`
  through `$answer-decision`, and a new task through `initiatives.mjs add`.

## Stamp it

Commit the work being summarised **first** - the digest is taken from `HEAD`,
so a brief describes committed work a reader can go and look at. Then:

```bash
node scripts/initiatives.mjs brief <slug> record
```

This writes `brief.generated_at`, `commit` and `digest` into
`initiative.json`. Never write those by hand; the digest is what makes
staleness computable instead of remembered. Commit the brief and the stamp
together.

## The brief is agent-owned

`wish.md` is the user's words and may never be rewritten. The brief is the
opposite: rewritten in full whenever the initiative moves, so a hand-edit is
discarded by the next refresh without a word. If the user corrects something in
a brief, fix the **document it summarised** - `spec.md`, `plan.md`,
`decisions.md` - and let the correction arrive here on the next write. Say that
when it comes up; a correction made only here is a correction that will be lost.
