# Flings critique - 2026-11-11

A review of the Flings application in `work/app/` in four respects: user
interaction, completeness of functionality, visual appearance, and coding
structure. Each item says what was observed and what to do about it. Items
marked **Done** were implemented in the change that added this file; the rest
are open suggestions.

## How it was reviewed

- The application was run locally with `npm run dev:local` at commit `90457f5`
  and used as an organizer (Casey) and as a member (Alex Morgan), at 1280 px
  and 390 px wide.
- Computed styles, heading outlines, page heights and scroll positions were
  measured with Playwright. The numbers quoted below come from those runs.
- All components, `app/globals.css`, `lib/http.ts`, `lib/event-time.ts` and the
  test scripts were read. `lib/access.ts`, `lib/journeys.ts` and the message
  and recovery libraries were read for their public operations, without a
  line-by-line audit.
- The hosted Test site was not used. Nothing here repeats the access-control
  and recovery verification recorded in the other notes.

## 1. Quality of user interaction

### U1. Put planning first on the organizer page - Done

The organizer page for a fling ran in this order: discussions, polls and
payments; message audience; save a backup; check a backup; delete the
gathering; open or closed state; activities and events; members. The two
things an organizer does most, planning activities and inviting members, were
below the backup and deletion tools, about 2,500 px down a 4,085 px page.

Now the order is: state, activities and events, members and organizers,
discussions/polls/payments, messages, and a last "Backup & deletion" section
holding the three recovery panels.

### U2. Section navigation on the organizer page - Done

The page was 4,085 px tall at 1280 px wide and 6,236 px at 390 px, with no way
to reach a section except scrolling. A bar of five links now sits under the
state row and stays at the top of the window while scrolling. At phone width
it scrolls sideways on one line.

### U3. Keep the scroll position when the window regains focus - Done

The workspace re-checks sign-in each time the window regains focus and hid its
records with the `hidden` attribute while doing so. The page collapsed to the
height of its heading and the browser reset the scroll position. Measured:
scrolled to 2,500 px, focus event, scroll position 0. An organizer who copied a
prompt, switched to their mail application and came back was returned to the
top of the page every time.

The records are still hidden the same way during the re-check, and their
wrapper now holds the height they had, so the document does not shrink.
Measured after the change: 2,500 px before, 2,500 px after.

A first attempt hid them with `visibility: hidden` instead. That kept the
height too, but the stock Button has `transition-all`, which animates the
inherited `visibility`; for a moment after the re-check a button still
computed as hidden and refused focus, and the coordination browser script
caught the lost focus return. See C1 for the general point about the stock
components and the global stylesheet.

### U4. Show confirmations and errors where the user is looking - Done

"Member profile created", "Invitation saved" and every other organizer
confirmation was written to an element under the page title. After an action
taken lower down, nothing visible changed. The confirmation now appears as a
fixed message at the bottom of the window, and an error scrolls its own report
into view. Scroll padding keeps focused controls clear of the message and of
the section bar.

Still open: the message stays until the next action. A dismiss control would
be a small addition.

### U5. Put invitations first on the member page - Done

A member opening their link saw "Discussions, polls & payments" with three
empty columns before the activities they were invited to. Invitations now come
first, with discussions, polls and payments under them in the same column and
contact details beside them. At phone width the order is invitations,
discussions, contact details.

### U6. Keep a member's unsaved typing across a focus re-check - Open

The member page clears its data when the window regains focus and loads it
again. Measured: type a new name without saving, focus event, the field shows
the saved name. A member who switches to another application to look up a
phone number loses what they typed. An open post draft is lost the same way
because the coordination panel unmounts.

Clearing the page is a recorded security decision, so the fix has to keep it:
hold the draft in memory only, and put it back when the re-check returns the
same member and the same profile revision. Discard it otherwise.

### U7. Add a co-organizer without an internal ID - Open

The Organizers panel asks for an "Existing organizer ID". No screen shows an
organizer their ID, so a second organizer cannot be added without reading the
database. Replace it with an invitation the new organizer accepts after
signing in: a single-use link, or an email address matched at sign-in with an
explicit acceptance step so that a matching address alone never grants access.

### U8. Enter and show money in ordinary currency amounts - Open

Payment requests ask for an "Amount in minor units (USD cents, JPY yen)" and
show "1500 USD minor units outstanding". Storage in minor units is right; the
interface should accept and show `15.00` and `$15.00`. `Intl.NumberFormat`
with `style: 'currency'` gives both the format and the number of decimal
places for a currency code.

### U9. Choose time zones from a list - Open

The event and fling forms take a typed IANA name such as
`America/Los_Angeles`, with a hint giving two examples. Offer a select filled
from `Intl.supportedValuesOf('timeZone')`, starting at the fling's default.

### U10. One readable event-time format - Open

The same event is shown three ways:

- organizer plan: `2026-10-03 18:00 (UTC−07:00) · America/Los_Angeles`
- member page: `Oct 3, 2026, 6:00 PM (UTC−07:00) · America/Los_Angeles`
- discussion, poll and ledger times: `toLocaleString()` in the viewer's own
  zone, with no zone shown

Use one format everywhere, for example `Sat, Oct 3, 6:00 PM PDT`, with the year
only when it is not the current one and the offset only around a clock change.
Where the viewer's zone differs from the event's, add their local time. See
C11.

### U11. Shorter visible button labels - Open

Buttons carry the full name of what they act on: "Edit profile for Alex
Morgan", "Move Movie & dinner up", "Add event to Movie & dinner". This is
good for a screen reader and long for everyone else, and it wraps at phone
width. Show "Edit", "Move up", "Add event" and keep the full wording in
`aria-label`, which must still begin with the visible text.

### U12. Reorder activities in both directions - Open

Activities have "Move up" only. Moving the first of six activities to the end
takes five clicks on five other cards. Add "Move down", or accept a position
number.

### U13. Coordination forms next to what they change - Open

Every coordination action opens one shared form at the top of the panel:
editing the last post in a long discussion opens a form above the first post.
All of its variants submit with "Save coordination". Open the form in place
and label the submit button for what it does: "Post", "Create poll", "Request
payment", "Record adjustment".

### U14. Pre-select poll voters - Open

"Review eligible members for this poll" starts with nobody ticked. The usual
poll goes to every accepted member, so start with all of them ticked and let
the organizer untick.

### U15. Confirm an invitation response beside its buttons - Open

After "Accept invitation" the text "Your invitation response is saved" appears
under the contact form, which at phone width is far below the button. The
badge on the activity changes, which is the only nearby feedback. Put the
message in the activity card.

### U16. Plain words in place of internal terms - Open

Wording that comes from the data model or the test programme reaches the
user: "Refresh coordination", "Save coordination", "Message audience",
"membership", "ledger adjustment", "Reported, unconfirmed", "Test rehearsal ·
fictional people", "Return to the rehearsals". A pass over the visible strings
with a member and a first-time organizer in mind would help, with the
rehearsal wording shown only in local and test modes.

### U17. Say why the message form is disabled - Open

"Write the message" is greyed out until "Review recipients" has run. Nothing
says so. Add one line: "Review recipients first."

### U18. Warn before leaving an open editor - Open

Following a link or closing the tab with an activity, event or post half
written discards it without a prompt. Register `beforeunload` while an editor
holds changes.

## 2. Completeness of functionality

Measured against `wish.md` and `objectives.md`.

### F1. Organizer controls for member links - Open

The wish makes a personal link the member's only way in. The API can issue,
replace and revoke a member's link (`lib/http.ts`, the `issue`, `replace` and
`revoke` branches), but no component calls any of them. The only way an
organizer obtains a link is inside the exported message prompt. Add to each
member card: "Copy link", "Replace link" with its existing confirmation, and
the list of current links with "Revoke". This is the highest-value open item.

### F2. Remove a member from the interface - Open

`removeMember` exists in the API and has no control. A member added by mistake
stays in the list.

### F3. Delete an activity or event - Open

An activity can be set to cancelled, which keeps a notice for invitees. Neither
an activity nor an event can be deleted, in the interface or the API, so a
draft created by mistake, or a duplicated event, stays. Allow deleting a draft
activity that has no invitations, and an event of a draft activity. Published
ones keep the cancel path.

### F4. Show members who is organizing and who is going - Open

The member page names no organizer and lists no other member. Someone invited
to a dinner cannot see who else accepted or who to ask. Show organizer names,
and offer the organizer a per-activity setting to show accepted members' names
to other accepted members. Contact details stay private.

### F5. Split a payment across members - Open

A payment request goes to one member. Sharing a 240.00 booking among eight
people means filling in the form eight times. Add "split equally among
accepted members" that creates the eight requests in one batch, with the
remainder assigned visibly.

### F6. Message drafting, sending and batch size - Open

The wish asks for AI agents that draft direct email or text messages. What
exists is a reviewed prompt the organizer copies into an outside tool, limited
to five deliveries per batch (`lib/messages.ts:181`), and outcomes the
organizer reports by hand. An 80-person wedding needs sixteen batches. In-app
drafting and direct delivery are deferred by decision; the batch limit is
described as a pilot limit and should be raised when the pilot ends.

### F7. Calendar file and map link for events - Open

A member cannot add an event to their calendar. Offer an `.ics` download per
event and per fling, generated from data the page already holds, and a map
link built from the street address when no location link was entered.

### F8. Mark what changed since the member's last visit - Open

An event shows "Updated" with a time. Nothing marks new posts, new polls or a
new payment request, so a returning member has to read everything again.
Record a last-seen time per member session and mark newer items.

### F9. A fuller list of the organizer's flings - Open

The organizer's list shows a state badge and a title. Add the date range,
member count and number of unanswered invitations, and put closed flings in
their own group.

### F10. Response summary per activity - Open

To learn who has not answered, an organizer reads each member's card. Add a
summary per activity: accepted, declined, no answer, each a count that opens
the names. The audience filter "Unanswered invitations" already computes this
for messages.

### F11. Bulk member import and bulk invitation - Open

Members are added one form at a time and invited one click per member per
activity. Forty members and three activities is 40 forms and 120 clicks. Add a
paste-a-list import and "Invite all members" on an activity.

### F12. Description and time zone when creating a fling - Open

"Create a fling" asks for a title. The description and default time zone are
set afterwards through "Edit fling details", a button in the Activities
section. Ask for them at creation, with the browser's zone as the default.

## 3. Visual appearance

### V1. Make button variants visible - Done

Every button looked the same: dark green with white text. The components
declared `variant="outline"` on thirty buttons and
`variant="destructive"` on "Delete this gathering…", but a rule in
`app/globals.css` set `background` and `color` on the `button` element outside
any cascade layer, which overrides Tailwind's utility classes. Measured before
the change: "Refresh coordination" (outline), "Write a post" (default) and
"Delete this gathering…" (destructive) all computed to `rgb(36, 85, 69)` with
white text.

The rule now sets size only. Primary actions are filled green, secondary ones
are outlined on a card background, and destructive ones (delete gathering,
remove organizer, hide post) are brick red. `--destructive` was mapped to the
palette; it reads 5.9:1 or better against its own tint on all three page
backgrounds.

### V2. One button height - Done

Buttons were 46 px tall in panels that set `height: auto` and 32 px elsewhere,
where the fixed height squeezed the padding. All buttons are now at least
40 px tall with the same padding, and wrap long labels.

### V3. Visible checkboxes, radio buttons and field borders - Done

Checkboxes were 16 px with a border of `oklch(0.922 0 0)`, the scaffold's
light grey, on a cream page: about 1.1:1. "Also post to one discussion" and "I
understand that this file contains unencrypted personal data" looked like
labels with no control. Field borders were `#b5bdb5`, 1.6:1 to 1.9:1.

`--input` is now `#74817a`, which is 3.4:1 to 4.0:1 against the page, panel and
card backgrounds. Checkboxes and radio buttons are 20 px on a card background.
Disabled fields use the muted panel colour.

### V4. Space between stacked panels - Done

"Your organizer profile" and "Create a fling" touched, as did the three
recovery panels and the two panels beside the member list. Adjacent panels now
have a 24 px gap.

### V5. Readable, coloured state labels - Done

States were shown as stored: `open`, `published`, `accepted`, `invited`. They
are now capitalised by the stylesheet and coloured by meaning: green for open,
published and accepted; amber for draft and invited; red for cancelled and
declined; blue-grey for closed. The stored text is unchanged, so tests and
screen readers read the same words.

### V6. One heading scale - Partly done

Done: member names were second-level headings inside a second-level section
and are now third-level; "Delete gathering" was an unstyled heading at body
size and now matches the other panels; the recovery panels sit under one
"Backup & deletion" heading.

Open: event titles on the member page are 14 px bold, smaller than the 16 px
text around them; the message panels use fifth-level headings directly under
third-level ones; card titles are serif in some panels and sans-serif in
others. Define sizes for four heading levels once and remove the per-panel
overrides.

### V7. Collapse the three empty coordination columns - Open

With no posts, polls or payments the panel shows three headed columns each
saying there is nothing. Show one line until something exists.

### V8. Raise the smallest text sizes - Open

Hints are 11 px (`.small`), footnotes and the header label 12 px, and field
labels 12 px on the member page. Use 13 px as the minimum, 14 px for labels.

### V9. Tidy the confirmation dialogs - Open

The dialogs are 384 px wide at most, so "Delete A movie, then dinner
permanently?" wraps to two lines at desktop width, the field label sits
against its input, and the two buttons are stacked full width. Widen to about
480 px, add the field spacing used elsewhere, and place the buttons in a row.

### V10. Decide on dark mode - Open

`globals.css` carries a full `.dark` palette from the scaffold. Nothing sets
that class and it is not mapped to the application's colours. Either remove
it or map it and follow `prefers-color-scheme`.

## 4. Coding structure

### C1. Move element rules in `globals.css` into cascade layers - Partly done

The cause of V1 is general: `globals.css` styles bare elements (`button`,
`header`, `article`, `h1`, `h2`, `p`, `hr`) outside any layer, so those rules
override the utility classes of every component, including the stock ones.
The `button` rule is fixed and documented in the file. The others remain: any
`<article>` gets a card background and a green top border, any `<header>` a
bottom border. Move element rules into `@layer base` and the application's
class rules into `@layer components`, so utilities and variants take
precedence in the order Tailwind intends.

### C2. One palette, formatted CSS - Open

There are two `:root` blocks; the second overrides part of the first, which is
how `--input` and `--destructive` were left at scaffold values. About forty
colours are written as hex literals beside the tokens. The first half of the
file is formatted and the second half is one declaration block per line.
Merge the blocks, name the remaining colours as tokens, and format the file.

### C3. Split `organizer-page.tsx` - Open

One component of about 950 lines holds sign-in, the list of flings, the
organizer profile, fling creation, state changes, members, invitations,
organizers and two confirmation dialogs, with sixteen `useState` calls and
markup indented up to eighteen levels deep. Suggested parts: a `useOrganizerSession`
hook for `request`, `refresh` and the sign-in state; `OrganizerWorkspace` for
the list; `FlingPage` for one fling; `MembersPanel`; `OrganizersPanel`.

### C4. Shared API types and a typed `request` - Open

Each component declares the response shapes it expects by hand. `Fling`,
`Activity`, `Event`, `Member` and `Scope` are declared two or three times, and
`request()` returns either `unknown` or one type that merges every response.
A field renamed on the server compiles on the client. Export the shapes from
the store functions' return types into one module and make `request<T>`
generic.

### C5. A route table in place of the `handle()` condition chain - Open

`handle()` in `lib/http.ts` is one function of about 450 lines that tests
positional path parts named `fling`, `action`, `member` and `sub` in about
ninety `if` tests. The names stop fitting early: `member` holds `audience`,
`recovery`, `messages` and `coordination`. A table of method, path pattern,
required actor and handler would make the endpoints listable, which also
gives the tests and the documentation something to enumerate.

### C6. Shared database row helper and checked SQL - Open

`type Row = Record<string, unknown>` is declared in eleven files. Queries are
long inline SQL strings, one of them about 900 characters, written apart from
the Drizzle schema in `db/schema.ts`, so a column rename is caught only when a
test reaches that statement. Share the row type and query helper, and either
build reads with Drizzle or add a test that prepares every statement against
the migrated schema.

### C7. Remove unused components and dependencies - Open

`components/ui/` holds 60 stock components; 43 are not imported by anything.
`recharts`, `embla-carousel-react`, `cmdk`, `react-day-picker`, `input-otp`
and `react-resizable-panels` are used only by unused components, and
`date-fns` by nothing. Removing them shortens installs and the dependency
audit, which the README records as having unresolved advisories.

### C8. Fix the lint error and run the checks in CI - Open

`npm run lint` fails on `main`: `components/member-page.tsx` reads
`credentials.current` during render, which the React compiler rule rejects.
Hold "has credentials" in state. No workflow under `.github/workflows/` runs
this application's type check, lint, unit tests or build, so nothing stops a
failing check from merging. Add a workflow limited to changes under
`initiatives/flings/work/app/`.

### C9. One browser-test command with a selectable engine - Open

There are twenty browser scripts. Each launches Chromium, Firefox and WebKit
itself and is run by hand; `npm run test:browser` runs one of them. An
environment with one engine installed cannot run them without patching.
Move the engine loop into a shared helper that reads an environment variable,
and give the suite one command.

### C10. Separate current documentation from dated receipts - Open

`work/app/README.md` is about 800 lines, mostly dated sections appended as
work was done. There are 69 files under `test/evidence/` and 59 under
`notes/`. Finding how something works today means reading its history. Keep
the README to what is true now, move dated sections to `notes/`, add an index
there, and keep only the latest receipt of each kind in `test/evidence/`.

### C11. One event-time formatter - Open

`member-page.tsx` builds the same `Intl.DateTimeFormat` three times inline,
`gathering-editor.tsx` prints ISO text, and `coordination-panel.tsx` uses
`toLocaleString()`. Add `formatEventTime(instant, zone)` to
`lib/event-time.ts` with unit tests around clock changes, and use it in all
three. This is the code side of U10.

### C12. One component per form - Open

`GatheringEditor` renders the fling, activity and event editors from one form
switched on a `kind` string, and `CoordinationPanel` does the same for posts,
polls, payments and ledger entries, with nested conditional expressions for
titles, labels and payloads. One small component per form, sharing a field
component, would be longer in total and far easier to change.

### C13. Shared page header and application name - Open

The header with the wordmark and "Test rehearsal · fictional people" is
written out in four components. The package is still named
`flings-access-foundations`. Make one `SiteHeader` that takes the mode, and
rename the package.

## What was implemented with this critique

Two areas, chosen because they affect every screen and every visit and could
be changed without touching access rules or stored data:

1. **Controls that can be told apart and seen** - V1 to V5, part of V6, and
   the `button` part of C1.
2. **Finding and keeping your place** - U1 to U5.

Checks run on the change: type check; 177 unit tests; the Sites build; the
local browser scripts on Chromium at both widths. Firefox and WebKit are not
installed where this was done, so the three-engine matrix has not been
repeated. The lint error in C8 predates the change and is still present.

## Suggested order for the rest

1. F1 and F2 - member link and removal controls. The API exists.
2. C8 - lint fix and CI, so later changes are checked.
3. U8, then U10 with C11 - money and time, the two places where stored values
   reach the screen unformatted.
4. U6 and U7 - the draft loss and the organizer ID field.
5. C7, C2 and the rest of C1 - removal and stylesheet tidy-up before more
   interface is added.
6. C3 to C5 - the structural changes, each with the browser scripts as the
   safety check.
7. F10, F11, F4, F5, F7 as the pilot shows which are missed most.
